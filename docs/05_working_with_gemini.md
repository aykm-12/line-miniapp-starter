# 5. Geminiとの付き合い方

このスターターをベースに自分のアプリを作っていく際、Claude Codeのようなコーディングエージェントではなく、Gemini（チャット形式のAI）とVSCodeを使って手動でコードをコピペしながら開発する想定です。Geminiはこのリポジトリの中身を自動では見てくれないため、Claude Codeとは違う付き合い方が必要です。

## 5-1. 前提: Geminiはリポジトリを知らない

- Geminiとのチャットは、あなたが貼り付けた内容しか見えません。「今どのファイルを触っているか」「プロジェクトの構成」は、会話のたびに自分で伝える必要があります。
- 会話が続いていても、前の会話で貼ったファイルの中身を正確に覚えているとは限りません。特に長い会話では、古い内容のまま回答してしまうことがあります。

## 5-2. 基本ルール

1. **修正したいファイルは全文を貼り付ける**（差分ではなく）。返してもらうときも「ファイル全体」を出力してもらいましょう。
2. **一度に頼む変更は1ファイル・1機能に絞る**。複数の機能をまとめて頼むと、意図しない箇所まで書き換えられがちです。
3. **プロンプトの冒頭に、このスターターの構成を一言添える**。例:
   - `src/App.vue`: LIFF初期化とログイン状態の表示を行うルートコンポーネント
   - `src/lib/liff.js`: LIFF初期化をラップする関数（`isLiffConfigured` / `initLiff` / `liff`）
   - `src/lib/supabase.js`: Supabaseクライアントの生成（`isSupabaseConfigured` / `supabase`）
   - `src/components/*.vue`: 画面の各パーツ（例: `SampleList.vue`はSupabaseとのCRUDサンプル）
   - `supabase/schema.sql`: テーブル定義とRLSポリシー
4. **使いたいLIFF/Supabaseの関数は、公式リファレンスのメソッドシグネチャを貼ってから実装を依頼する**。Geminiは学習データの中に古いバージョンのAPIも混ざっているため、何も渡さないと存在しない引数や古い書き方を出してくることがあります（詳しくは5-3）。
5. **返ってきたコードは「何を変えたか」を説明させてから貼り付ける**。複数ファイルにまたがる変更を頼むときは、先に「どのファイルを触る予定か」を一覧で確認してから実装させましょう。

## 5-3. よくある失敗パターンと対策

| 失敗パターン | 具体例 | 対策 |
| --- | --- | --- |
| 存在しない/古いAPIをでっち上げる | `liff.sendMessage`（単数形）のような存在しない関数名、Supabase JS v1の`.insert(単一オブジェクト)`構文など | 実装を頼む前に、公式リファレンスのメソッドシグネチャをそのままチャットに貼る |
| リポジトリ構成を忘れて重複ファイルを作りたがる | 既にある`src/lib/supabase.js`を無視して`src/utils/supabaseClient.js`を新規に提案してくる | プロンプト冒頭で毎回ディレクトリ構成を共有する（5-2の3.） |
| 「機能Xを追加して」で全体を書き直され、既存コードが消える | ボタンを1つ足しただけのつもりが、Supabaseの取得処理ごと消えて返ってくる | 「既存のコードは変更せずに追加してください」と明記し、必ずファイル全体で返してもらう |
| 間違ったファイルを直そうとする | エラーメッセージだけ貼ると、無関係なファイルの修正案が返ってくる | どのファイルの話か、パスを毎回明示する |
| `.env`の中身をそのまま貼ってしまう | LIFF IDやSupabaseキーを含めた`.env`をコピペして質問してしまう | 質問する前にキーの値をダミー文字列に置き換える |
| LIFFはLINEアプリ内/HTTPS前提であることを踏まえない提案 | 素のブラウザでの動作を前提にしたコードを提案してくる | `liff.isInClient()`で分岐する現状の実装（`src/App.vue`）を踏まえて質問する |
| Vite特有の環境変数の書き方を間違える | `import.meta.env.VITE_X`ではなく`process.env.X`と書いてしまう（Node.js向けの書き方と混同） | 「これはVite製のVueアプリなので、環境変数は`import.meta.env.VITE_X`で参照する」と明記する |

## 5-4. コピペ用プロンプトテンプレ例

**新しい機能を1つ追加したいとき**
```
これはLINEミニアプリ（Vue3 + Vite + @line/liff + Supabase）のプロジェクトです。
以下は src/components/SampleList.vue の現在の内容です。

（ここにファイル全体を貼り付け）

このファイルに、〇〇の機能を追加してください。
- 既存のコードは変更しないでください
- 変更後のファイル全体を出力してください
- 何を変更したか、最後に箇条書きで説明してください
```

**LIFFの発展機能を使いたいとき**
```
@line/liff の以下のメソッドを使って、〇〇を実装したいです。

（公式リファレンスからメソッドシグネチャ・使用条件を貼り付け）

現在のsrc/lib/liff.js の内容は以下です。

（ファイル全体を貼り付け）

この構成に沿って、liff.jsに関数を追加する形で実装案を提示してください。
```

**エラーが出て直したいとき**
```
以下のファイル（src/App.vue）を実行すると、次のエラーが出ます。

エラーメッセージ: （貼り付け）

ファイルの内容:
（ファイル全体を貼り付け）

原因と、修正後のファイル全体を教えてください。
```

## 5-5. ファイルが長くなりすぎたら

`App.vue` や特定のコンポーネントに機能を追加し続けると、1ファイルの行数が増えて見通しが悪くなることがあります。そうなったら、新機能を追加する前に一度AIアシスタント（Gemini・Claude Codeなど）に「このファイルを機能ごとに分割してリファクタリングしてほしい」と頼んでみるのも一つの方法です。5-2のルールと同様、ファイル全体を貼り付けて依頼し、リファクタリング後は必ず動作確認をしてから次の変更に進んでください。
